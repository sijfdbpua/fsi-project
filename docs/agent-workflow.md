# Совместная работа двух участников и их агентов

## Модель работы

У каждого участника — свой GitHub-аккаунт, ноутбук/облачная задача и чат с агентом.
Общее состояние хранится в репозитории, Issue и PR. Сообщение одному агенту
не доставляется другому автоматически. Локальные субагенты одного сеанса тоже
не являются агентом вашего друга.

Процесс: **задача → владелец и границы → ветка → реализация → проверки → PR →
ревью вторым участником → merge → закрытие задачи**.

Для опечатки достаточно короткого описания и проверки документа. Для изменения
нескольких компонентов нужны зависимости и согласованный контракт. Процесс
не требует выделенного «агента-архитектора», огромного плана и полного набора
тестов для каждой мелочи.

## Первоначальная настройка

Выполняется один раз владельцем репозитория после попадания этих файлов в `main`.

1. Проверьте, что оба участника приняли приглашения и могут читать репозиторий
   и отправлять свои ветки. Каждый подключает GitHub в своём инструменте.
   Не передавайте друг другу токены и пароли.
2. Убедитесь, что включены Issues. Форма **Задача для агента** должна появиться
   при создании Issue после добавления шаблона в основную ветку.
3. В GitHub **Settings → Rules → Rulesets** либо **Branches → Branch protection**
   задайте защиту `main`, если это поддерживается тарифом и типом репозитория:
   требовать PR, одно одобрение другого участника, закрытие обсуждений,
   сброс устаревших одобрений после новых изменений; запретить force push и удаление.
   Проверяйте, что правило активно и у пользователей/приложений нет ненужного bypass.
4. Когда появится CI, добавьте реальные имена его обязательных checks в защиту.
   До появления CI не требуйте вымышленные проверки: это заблокирует merge.
   Для двух участников без merge queue интегрируйте PR по очереди и обновляйте
   второй после первого. При CI можно требовать актуальность ветки перед merge.
5. Зафиксируйте, кто сливает PR. По умолчанию это человек после ревью;
   полномочия на автоматический merge выдаются отдельно и явно.

Эти настройки не были применены или проверены созданием документов. Если защита
недоступна, договорённость сохраняется, но технического запрета нет. Создание
GitHub Project с колонками статусов необязательно: для старта достаточно Issue и PR.
Шаблоны сами не назначают исполнителей, не меняют статусы и не запускают CI.

## Роли на одну задачу

| Роль | Ответственность |
| --- | --- |
| Координатор — один из вас | Определить результат, владельцев, зависимости и порядок интеграции |
| Исполнитель — участник и его агент | Изменения в своей ветке, проверки, описание PR, исправления |
| Reviewer — второй участник и его агент | Независимо проверить критерии, diff и свидетельства проверок |
| Интегратор — назначенный участник | Проверить разрешение на merge, актуальный PR, проверки и порядок слияния |

Роли меняются между задачами. Когда вы оба реализуете независимые задачи,
проверяйте PR друг друга. Автор PR не может одобрить собственный PR своим
GitHub-аккаунтом. Для ревью используйте аккаунт второго участника. Агент может
подготовить выводы, а участник оформить review, если у инструмента нет нужного доступа.

## Планирование и распределение

1. Опишите цель функции и критерии результата. Для нового проекта сначала
   заполните [контекст](project-context.md) по известным требованиям.
2. Разбейте работу на отдельные результаты. Для каждой задачи укажите
   одного исполнителя, другого reviewer, затрагиваемые компоненты, исключения,
   зависимости и способ проверки. Используйте шаблон Issue.
3. До параллельной реализации согласуйте общий API, формат данных или другой
   интерфейс в родительской задаче/документе. Изменения контракта сообщаются
   второму владельцу до изменения зависимого кода.
4. API, миграции, корневой конфиг, зависимости и lockfile назначайте одному
   владельцу на этап. Если обе задачи требуют их менять, выделите общую
   подготовительную задачу либо выполняйте задачи последовательно.
5. Запишите порядок merge. Не считайте зависимую задачу готовой только потому,
   что её заглушка или локальная версия работает отдельно.

Пример: сначала отдельный PR с согласованным контрактом; затем параллельно
реализация сервиса и интерфейса по этому контракту; после их интеграции — сквозной
сценарий. Проверки с mock-данными полезны, но не подтверждают интеграцию с сервисом.

## Занять задачу без гонки

Задача готова к реализации, когда у неё есть цель, критерии, границы и согласованный
владелец. Предпочитайте заранее назначать задачи друг другу, а не одновременно
забирать одну из общей очереди.

Исполнитель читает Issue, assignee, последние комментарии и связанные PR,
проверяет отсутствие другого исполнителя и фиксирует запись:

```text
Статус: In Progress
Исполнитель: @alex
Reviewer: @sam
Ветка: agent/alex/12-login
Границы: перечисление компонентов/файлов
Зависимости: нет известных / #номер
Следующий шаг: конкретное действие
```

Перед редактированием ещё раз проверьте состояние. GitHub-комментарии и assignee
не дают атомарной блокировки. Если уже работают двое, остановите пересекающиеся
изменения, сохраните локальную работу и явно согласуйте владельца. Тайм-аут,
молчание друга или «старый» комментарий не разрешают перехват задачи.

Если исполнитель недоступен, отметьте Blocked и обратитесь к координатору или
пользователю. Он может явно переназначить задачу, зафиксировав решение в Issue.
Новый исполнитель начинает в новой ветке, сохраняет прежнюю ветку и учитывает
уже сделанное. Вернувшийся участник сначала проверяет новое назначение и не
продолжает старую реализацию параллельно. Сам тайм-аут владение не передаёт.

Состояние храните в описании/комментариях Issue. Не используйте общий `TASKS.md`
как блокировку: разные клоны видят разные версии. Служебные статусы могут публиковаться
только в пределах разрешения пользователя; при его отсутствии передайте готовый
текст человеку для публикации.

## Ветки и рабочие копии

Одна рабочая копия на активную облачную задачу или отдельный клон на ноутбуке.
Облако уже изолирует задачи: не создавайте worktree без явного запроса.
Не запускайте двух исполнителей с правом менять одни файлы в одном checkout.

Перед началом посмотрите состояние:

```bash
git status --short --branch
git branch --show-current
git fetch origin
```

Если текущая ветка уже выделена платформой, оставайтесь в ней и укажите её имя
в Issue. На чистом локальном клоне без выделенной ветки можно создать новую
от свежего `origin/main`. Ниже только пример для задачи #12 участника alex;
используйте своё уникальное имя:

```bash
git switch -c agent/alex/12-login origin/main
```

Не выполняйте переключение поверх незавершённой чужой работы. Перед коммитом
просмотрите diff и добавляйте только свои файлы. Отправка ветки и создание PR
допустимы, когда пользователь разрешил это для задачи. В облаке кнопка создания
PR также может быть доступна вместо CLI; не требуйте новый токен лишь потому,
что `gh` не авторизован, если платформа умеет выполнить нужное действие.

Перед сдачей, находясь в своей ветке и сохранив незавершённую работу, обновите
сведения о базе. Если `main` ушла вперёд, интегрируйте её по правилам проекта.
Стандарт этого процесса — merge, сохраняющий опубликованную историю:

```bash
git fetch origin
git merge origin/main
```

При конфликте прочитайте обе реализации и связанные задачи. Не применяйте ко
всем файлам `ours` или `theirs`. После разрешения снова запустите затронутые
проверки. Не используйте force push, hard reset и удаление чужой ветки для
синхронизации. Если в другом проекте принята иная стратегия, сначала отразите
её в его правилах.

## Проверки, ревью и интеграция

Исполнитель проверяет результат командами из контекста и реальных файлов проекта.
Примерный выбор по изменению:

| Изменение | Нужное свидетельство |
| --- | --- |
| Логика | Релевантные тесты, включая изменённое условие и важные ошибки |
| Интерфейс | Запуск и пользовательский сценарий; для визуальных изменений — доступные скриншоты |
| API/БД | Контракт, обработка ошибок, релевантная интеграция; для миграции — безопасная проверка и откат |
| Зависимости/конфиг | Установка по lockfile и затронутые build/start/test |
| Только документы | Ссылки, формат, согласованность и выполнимость инструкций |

Не каждый пункт таблицы нужен каждой задаче. Если код не появился, сборки и
тестов приложения ещё нет — не называйте их пройденными. Ошибки среды и известные
дефекты отмечайте отдельно; обязательная заблокированная проверка остаётся блокером.

Создайте PR с заполненным шаблоном и ссылкой на Issue. Для незавершённой работы
используйте Draft PR, явно указав оставшиеся шаги. Reviewer сверяет задачу,
актуальные SHA и базу, читает diff, проверяет значимые сценарии и сообщает
блокирующие дефекты отдельно от пожеланий. При невозможности проверки пишет,
что именно не удалось; отсутствие найденных проблем не равно доказанной корректности.

Исполнитель исправляет замечания. Изменённый после ревью PR проверяется снова;
обновлённая база может потребовать повторной проверки интеграции. Интегратор
сливает по одному PR только после выполнения критериев, устранения блокеров,
нужных проверок и одобрения другого участника при наличии разрешения на merge.
Участники затем обновляют свои копии. Деплой — отдельный шаг с отдельным разрешением.

## Состояния и передача

Статусы — текстовая договорённость; GitHub не переключает их автоматически:

| Статус | Значение / следующий переход |
| --- | --- |
| Draft | Цель уточняется; после критериев и распределения → Ready |
| Ready | Владелец определён, блокирующие зависимости сняты; начало → In Progress |
| In Progress | Реализация; локальная готовность и PR → Review |
| Review | PR ожидает проверки; дефекты → Changes Requested, готовность → merge |
| Changes Requested | Исполнитель исправляет блокирующие замечания; затем → Review |
| Blocked | Указаны причина, нужное действие и ответственный; после снятия → предыдущий этап |
| Done | Критерии и проверки выполнены, review пройден, PR вошёл в основную ветку |

Независимые шаги во время блокера продолжайте. Не закрывайте задачу как Done
при одном лишь успешном коммите или созданном PR. Отменённую задачу закрывайте
с объяснением отмены. Для передачи другому участнику используйте запись:

```text
Задача и PR: ссылки
Владелец до/после: @alex → @sam (передача согласована)
Ветка и commit SHA: ...
Сделано: ...
Проверки: директория, точные команды, результаты, проверенный SHA
Не выполнено / блокер: ...
Настройки: только имена, без секретов
Следующий шаг: ...
```

Незакоммиченные изменения не доступны на другом ноутбуке. Сначала сохраните
их согласованным способом и передайте ветку; не начинайте параллельно менять
её с двух машин. При недоступном GitHub передавайте статус через человека,
не утверждая, что удалённое состояние обновлено.

## Промпты для ваших чатов

Замените имена, номера и ссылки реальными. Это примеры полномочий для будущих
задач, а не разрешение задним числом выполнять действия в текущем чате.

### Планирование общей функции

```text
Прочитай AGENTS.md и контекст проекта. Цель: [описание]. Нас двое:
[@первый] и [@второй], у каждого свой агент и checkout.
Составь минимальный план с критериями, границами, общими контрактами,
зависимостями, владельцем/reviewer каждой задачи и порядком merge.
Используй известные требования; спроси только то, без чего нельзя двигаться.
Создай согласованный набор Issue и опубликуй план в родительской задаче.
Публикацию этих задач и статусов разрешаю. Реализацию пока не начинай.
```

### Исполнитель

```text
Прочитай AGENTS.md. Выполни Issue [ссылка/номер] как агент [@логин].
Проверь владельца, актуальные зависимости и отсутствие пересечения задач.
Доведи реализацию и релевантные проверки до результата; исправляй обнаруженные
проблемы в рамках задачи. Используй выделенную ветку либо создай отдельную.
Разрешаю коммиты, push своей ветки, создание PR и статусы в этой задаче/PR.
Reviewer: [@второй]. Merge и деплой не разрешаю. Не запрашивай повторно
разрешение на уже перечисленные действия. В конце дай результат и доказательства.
```

### Reviewer

```text
Прочитай AGENTS.md. Проверь PR [ссылка/номер] по связанному Issue.
Работай с актуальным diff, проверь критерии, ошибки, интеграцию и тесты.
Свою рабочую копию с незавершённой работой не переключай и не сбрасывай.
Код автора не меняй. Опубликуй review в этом PR: конкретные блокеры с файлами,
строками, условиями и последствиями, отдельно необязательные предложения.
Публикацию этого review разрешаю. Укажи проверенный SHA, выполненные проверки
и ограничения. Если блокеров нет и критерии проверены, оформи одобрение
от моего аккаунта, если у него есть право. Merge и деплой не выполняй.
```

### Продолжение после перерыва

```text
Прочитай AGENTS.md, Issue [номер], последний статус и связанный PR.
Проверь текущую ветку, diff, владельца и изменения базы. Продолжи с последнего
подтверждённого шага, сохраняя чужую работу и прежние границы полномочий.
Не повторяй уже выполненные действия без причины; устаревшие проверки обнови.
```

## Перенос на другой проект

Сохраните его существующие инструкции, затем объедините с этим процессом.
Обновите пути, ссылку на репозиторий, название основной ветки и Git-стратегию
во всех документах и шаблонах; заполните контекст по реальным манифестам и CI.
Не копируйте утверждения о пустом репозитории в существующее приложение.
Защиту веток, доступы и secrets настраивают отдельно для каждого репозитория.
